# Загрузчик и LoadingCache в Caffeine

Примеры к этому тексту — `src/test/java/io/github/olaaa/cachinglab/caffeine/CaffeineCacheKindsTest.java`. Он работает без Spring и без БД, запускается за секунду.

## Коротко

- Загрузчик (loader) — функция «ключ → значение из источника». Её вызывает сам кэш, когда значения для ключа нет.
- Загружающий кэш (loading cache) — кэш, которому загрузчик отдали один раз при создании: `Caffeine.newBuilder()….build(loader)`. Дальше код просит у него просто `get(key)` и не знает, откуда берётся значение.
- Без загрузчика кэш — хранилище с `getIfPresent` и `put`. Куда идти при промахе, решает вызывающий код. Это и есть Cache-Aside.

Слово «loading» в имени типа значит не «сейчас загружается», а «умеет загружать сам».

## Четыре вида кэшей

Caffeine различает кэши по двум признакам: задан ли загрузчик и что хранится — значение или `CompletableFuture` со значением.

| Что хранится | Загрузчика нет | Загрузчик задан при создании |
|---|---|---|
| Значение | `Cache` — `build()` | `LoadingCache` — `build(CacheLoader)` |
| `CompletableFuture` | `AsyncCache` — `buildAsync()` | `AsyncLoadingCache` — `buildAsync(loader)` |

У `AsyncCache` и `AsyncLoadingCache` есть `synchronous()` — тот же кэш с блокирующим API. Хранилище одно, меняется только способ к нему обращаться.

## Загрузчик или функция в `get(key, function)`

У `Cache` тоже можно загрузить значение атомарно: `cache.get(key, function)`. Если ключа нет, Caffeine вызовет функцию, положит результат и вернёт его; второй вызов того же ключа подождёт первого. Получается тот же «вычисли, если нет» (compute if absent), что и у `LoadingCache.get(key)`.

Разница в том, кто знает, как загружать:

- `Cache.get(key, function)` — функцию передают в каждом вызове. Её знает каждое место вызова, и в двух местах она может оказаться разной.
- `LoadingCache.get(key)` — загрузчик знает сам кэш. Места вызова его не видят.

Тест: `ManualCache.mappingFunctionIsPassedOnEveryCall` против `LoadingCacheExamples.loaderIsGivenOnceAtBuildTime`.

## Зачем нужен загрузчик

1. Одно место загрузки. Логика «как получить товар по id» описана один раз, при создании кэша. Её нельзя забыть или написать по-разному в двух сервисах.
2. Защита от лавины промахов. `LoadingCache.get` и `Cache.get(key, function)` загружают ключ один раз, остальные запросы ждут результата. Наивный код «`getIfPresent`, при промахе загрузить и `put`» этого не даёт: все, кто пришёл до первого `put`, идут в источник (сценарий 6, `Scenario6StampedeTest`).
3. Обновление без участия клиента. `refresh(key)` и `refreshAfterWrite` перечитывают значение в фоне, а для этого кэш должен сам знать, как его загрузить. Поэтому `refreshAfterWrite` без загрузчика не собирается: `build()` бросает `IllegalStateException` с текстом «refreshAfterWrite requires a LoadingCache» (тест `refreshAfterWriteRequiresLoader`, сценарий 7).
4. Пакетная загрузка. `getAll(keys)` отдаёт загрузчику сразу все отсутствующие ключи через `loadAll` — один запрос `WHERE id IN (…)` вместо N запросов (тест `getAllLoadsMissingKeysWithOneBulkCall`).

В терминах шаблонов: кэш без загрузчика — Cache-Aside, приложение само ходит в источник. Кэш с загрузчиком — Read-Through: приложение спрашивает только кэш, а в источник ходит кэш.

## Что умеет `CacheLoader`

Обязателен только `load`, остальные методы имеют реализацию по умолчанию.

- `load(key)` — загрузить одно значение. Вернуть `null` — значит «значения нет»: запись не создаётся, `get` вернёт `null`, следующий вызов снова пойдёт в источник (тест `loaderReturningNullMeansNoEntry`, сценарий 8).
- `loadAll(keys)` — загрузить несколько. По умолчанию вызывает `load` для каждого ключа по очереди; переопределяют, когда у источника есть пакетный запрос.
- `reload(key, oldValue)` — перезагрузка для `refresh`. По умолчанию просто вызывает `load`; переопределяют, когда новое значение можно получить дешевле, зная старое (например, запросить только изменения с версии старого).
- `asyncLoad`, `asyncLoadAll`, `asyncReload` — те же операции для асинхронного кэша. По умолчанию запускают синхронные версии на `executor`.

## Синхронный и асинхронный кэш

`Cache` и `LoadingCache` хранят готовые значения. Загрузка идёт в потоке того, кто вызвал `get`, и он ждёт.

`AsyncCache` и `AsyncLoadingCache` хранят `CompletableFuture`. Future кладётся в кэш сразу, до того как загрузка закончится, поэтому второй запрос того же ключа получает ту же незавершённую future и ничего не запускает (тест `concurrentCallersShareOnePendingFuture`).

Загрузчик для асинхронного кэша бывает двух видов:

- `AsyncCacheLoader` — `(key, executor) -> CompletableFuture`. Для неблокирующих источников: R2DBC, `WebClient`, асинхронный клиент Redis. Загрузчик только запускает операцию и сразу возвращает future (тест `asyncLoaderReturnsFuture`).
- Обычный `CacheLoader` в `buildAsync(loader)`. Для блокирующих источников: JDBC, `RestClient`. Caffeine сам запускает его на `executor`, по умолчанию `ForkJoinPool.commonPool()` (тест `blockingLoaderRunsOnExecutorNotOnCallerThread`). Для долгих блокирующих вызовов лучше передать свой `executor` в `Caffeine.newBuilder().executor(…)`, чтобы не занимать общий пул.

## Загрузчик в реактивном коде

В этом проекте источник — `Mono<Product>`, поэтому все кэши асинхронные, а `Mono` превращается в future:

```java
cache.get(id, (key, executor) -> source.load(key).toFuture())
```

и обратно:

```java
Mono.fromFuture(() -> cache.get(…), true)
```

Что важно:

- `toFuture()` подписывается на `Mono` без Reactor Context вызывающего кода. Транзакция реактивного Spring живёт в контексте, поэтому загрузчик в неё не попадает и читает БД по своему соединению (сценарий 5).
- Пустой `Mono` даёт future с `null`. Caffeine такую запись не хранит — отсутствующий товар каждый раз идёт в источник. Если это мешает, храните `Optional` (сценарий 8). Удаляет её Caffeine в колбэке завершения future, поэтому сразу после ответа пустая запись ещё может быть видна.
- `Mono.fromFuture(supplier, true)`: supplier — чтобы кэш читался при подписке, а не при сборке цепочки; `true` — чтобы отмена одного подписчика не отменила общую future, которую ждут другие.
- В загрузчике нельзя вызывать `block()`: в WebFlux он работает на потоке event loop.

## Ошибки загрузчика

- `load` бросил исключение — запись не создаётся. `LoadingCache.get` пробрасывает его (проверяемое — внутри `CompletionException`), у асинхронного кэша future завершается с ошибкой и удаляется из кэша. Следующий запрос попробует загрузить снова.
- Упала перезагрузка (`refresh`, `refreshAfterWrite`) — остаётся старое значение, Caffeine пишет предупреждение в лог (сценарий 7).

## Загрузчик в Spring

С `@Cacheable` роль загрузчика играет тело аннотированного метода: при промахе Spring вызывает метод и кладёт результат в кэш. Отдельный `CacheLoader` можно задать через `CaffeineCacheManager.setCacheLoader(…)` (для асинхронного режима — `setAsyncCacheLoader(…)`). Тогда кэши менеджера становятся загружающими, и для них начинает работать `refreshAfterWrite` из спецификации Caffeine.

## Где это в проекте

- `Cache` без загрузчика — `NaiveCacheAsideProductService` (наивный Cache-Aside).
- `AsyncCache` и функция в `get` — `CacheAsideProductService`, `NegativeCachingProductService`.
- `AsyncLoadingCache` с загрузчиком — `RefreshAheadProductService`: без загрузчика `refreshAfterWrite` не работал бы.

## Как ответить на собеседовании

«Загрузчик — это функция, которой кэш сам получает значение по ключу при промахе. `LoadingCache` получает её при создании, поэтому вызывающий код просто делает `get` — это Read-Through. Загрузчик даёт одно место загрузки, атомарную загрузку без лавины промахов, пакетную загрузку через `getAll` и фоновое обновление: без загрузчика `refreshAfterWrite` в Caffeine невозможен. Асинхронные варианты хранят `CompletableFuture`, поэтому параллельные запросы одного ключа ждут одну загрузку; для реактивного источника я передаю `AsyncCacheLoader` и превращаю `Mono` в future».
